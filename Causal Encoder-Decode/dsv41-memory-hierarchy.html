六级层级总览 HBM → KV Cache → Index Cache → Engram → Host/SSD → Replay
1
HBM 常驻
权重 552B backbone ＋ 全部 cache ＋ engram 表。静态占用，与 seqlen 无关。40 层每层 window_kv_cache 在 __init__ 里一次性分配。
权重 ~500–552 GB + engram 202.8 GB
↓ 缩小到 seqlen 相关
2
KV Cache
两级：SWA 环形窗口（128 槽，不增长）＋ 压缩 KV（只有 4 个 kv_source 层拥有，其余层读它们）。
SWA 528 B/tok（增量 0） ＋ 压缩 720 B/tok
↓ 索引侧另立一份，精度更低
3
Index Cache
indexer 的 K，索引头只有 128 维（vs 主 KV 512），fp4。8 个 index_source 层拥有；Reuse 层直接复用上层算好的 top-k 索引，不占增量。
442 B/tok（1M ctx = 442 MiB）
↓ 不是 cache，但同处 HBM 且决定访存
4
Engram
查表型：整表常驻但每 token 每层只命中 24 行（L1/L14 两层共 48 行），不随 seqlen 增长。官方 196B 参数，不计入 552B backbone。
表 202.8 GB　／　每 tok 读 12.4 KiB
↓ 只有可重建/可换出的部分才下沉
5
Host / SSD
持久化压缩 KV ＋ indexer K。SWA 全量刻意不落盘——否则 1M ctx 要多存 20.6 GiB。
1M ctx ≈ 1.13 GiB（720+442 MiB）
↓ 缺的 SWA 状态由此重建
6
Replay
SWA Bounded Replay：只回放最近 n_win = 128 个 token 即可重建整层 SWA 环，不需持久化。
66 KiB / 层　（128 槽 × 528 B）
层级设计的核心不是"分层"，而是"只有少数层真正拥有缓存"。40 层里只有 4 层拥有压缩 KV、8 层拥有 indexer K， 其余层全部读归属层的那一份；加上 Reuse 层复用上层的 top-k 索引，才把每 token 的 KV 增量压到 1,162 B（官方口径 890 B）。

为什么索引缓存能和主 KV 分开量化：两者用途不同 —— 主 KV 要被 sparse_attn 做真正的注意力， 索引 K 只用来打分选位置（einsum("bshd,btd->bsht") 后取 top-512），所以能用更粗的 128 维 + fp4。 代码里两者的量化参数也不同：压缩 KV 用 16 通道 + E4M3，indexer 用 32 通道 + E8M0（model.py:546 vs :760）。

层级图里最容易读错的一点：engram 表虽然常驻 HBM 202.8 GB，却不是带宽瓶颈——一个 token 走完全部 40 层时， 两层表合计只读 12.38 KiB，相对下面那个权重流量可忽略。
但同一级的 engram.wkv 是真正的 Linear（6144→25600），每步必须全量读，两层 314.7 MB —— 这才是这一级的实际访存成本。 所以"Engram 在层级里很大"和"Engram 很贵"是两件事。
关于对照值 15.883 GB/token 的来历（此处应给出推导，否则会被当笔误）：它是 decode 单步的权重读带宽， 等于"每 token 激活的 ≈15.9B 参数 × 各自字节宽"（其中 6 个路由专家是 fp4 半字节，其余 fp8）之和，随本图一起现算。 注意它与"552B 全参"的关系是 552 GB ÷ 15.883 GB ≈ 34.8×：只有被激活的那一部分才需要读。
官方口径：Engram = 196B 参数，"sparsely accessed via token-based lookup"；本机算纯 fp8 数据 196.62 GB（含 scale 202.8 GB），吻合。 它不计入 552B backbone。

与官方口径的关系（两种算法并列，请自行判断）：
官方 model card 给的是 global KV cache = 890 B/token（约 V4-Flash 的 1/4）。
· 若按真实增长量（压缩 KV ＋ indexer K）＝ 1,162 B/token，为官方的 1.31×。
· 若把非增长的 SWA 528 B 也计入 ＝ 1,690 B/token，为官方的 1.90×。
上一版只摆了 1.90×，容易被误读成"官方口径缩水近一半"；本版两个都列，并标明 SWA 那一项真实增长量是 0。
差额（无论取哪个口径都存在）很可能来自 KV / indexer K 在层间的共享口径与去重方式——model card 只给最终压缩后数字， 未提供逐项拆分，因此本图不反推 890 的构成。
可以确定的是量级与结构：SWA 环是 O(window)=常数、压缩 KV 是 O(seqlen/r)、indexer K 只有 128 维所以远比主 KV 便宜 —— 这三条都由 model.py 的 buffer 形状直接决定。
需注意的口径与不确定项：
① 本表算的是"每层每 token 摊销"：SWA 记一个 slot（528 B），压缩 KV 记 288 B/r。这是稳态增长速率， 不是某一时刻的瞬时占用（压缩 KV 会攒满整段序列）。
② SWA 的"528 B/token"不是增长量：环形缓冲固定 128 槽、总量恒定 66 KiB/层，真实增长量是 0。 该行应读作"窗口内每个可见位置对应的字节"。
③ 单位：GB/MB 按 10⁹/10⁶ 字节；MiB/GiB 按 2²⁰/2³⁰。1M ctx = 2²⁰ = 1,048,576 token—— 这一点很关键：720 B × 2²⁰ = 720.0 MiB，而 720 B × 10⁶ = 686.6 MiB，两者差 4.6%。
④ batch size 影响：所有 cache 的第一个维度都是 max_batch_size（代码默认 4），本图按 B=1 计。
⑤ 权重字节数：552B 是参数个数（官方口径）。因专家为 fp4（0.5 B/参数），实际原始字节小于 552 GB， 故图中记 ~500–552 GB；552 GB 是"按 1 B/参数上界估"。
⑥ 890 B/token 与 1/8 持久化 均为 model card 引用值，非本图推导。
